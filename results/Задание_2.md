# Задание 2. Ключ сортировки и объём чтения

## 2.1. Подготовка

Созданы две копии истории за 13–26 октября с одинаковыми типами, кодеками и настройками. Ключи — `ended_at` и `(country, ended_at)`. После загрузки для каждой таблицы один раз выполнен `OPTIMIZE ... FINAL`.

[Проверка частей и количества событий](../02_order_by.sql#L46):

| table | active_parts | events |
| --- | --- | --- |
| hw_events_country | 1 | 10000000 |
| hw_events_time | 1 | 10000000 |

В каждой таблице по одной активной части и 10 млн событий. Дальше данные этих таблиц не менялись.

<details>
<summary>Определения таблиц из SHOW CREATE TABLE</summary>

[Первый запрос](../02_order_by.sql#L58):

```sql
CREATE TABLE takt.hw_events_time
(
    `ended_at` DateTime('UTC') CODEC(Delta(4), ZSTD(1)),
    `user_id` UInt64,
    `track_id` UInt64,
    `country` String,
    `platform` String,
    `app_version` String,
    `played_seconds` UInt32,
    `track_seconds` UInt32
)
ENGINE = MergeTree
ORDER BY ended_at
SETTINGS index_granularity = 8192, index_granularity_bytes = 0
```

[Второй запрос](../02_order_by.sql#L61):

```sql
CREATE TABLE takt.hw_events_country
(
    `ended_at` DateTime('UTC') CODEC(Delta(4), ZSTD(1)),
    `user_id` UInt64,
    `track_id` UInt64,
    `country` String,
    `platform` String,
    `app_version` String,
    `played_seconds` UInt32,
    `track_seconds` UInt32
)
ENGINE = MergeTree
ORDER BY (country, ended_at)
SETTINGS index_granularity = 8192, index_granularity_bytes = 0
```

</details>

**Прогноз перед опытом.** Для Германии составной ключ должен помочь: можно ограничить и страну, и время внутри неё. Для всех стран ключ по времени выглядит удобнее, потому что нужный день образует общий временной диапазон, а при сортировке по стране он разбит между группами стран.

## 2.3. Выводы

### Сравнение чтения

Для Германии ключ `(country, ended_at)` сократил отбор со 102 до 8 гранул и чтение с 835.58 до 65.54 тыс. строк — примерно в 12.7 раза. Объём снизился с 15.04 до 1.18 MB.

Для всех стран лучше оказался `ended_at`: 102 гранулы и 15.04 MB против 114 гранул и 16.77 MB у составного ключа. Прочитано соответственно 835.58 и 931.46 тыс. строк.

### Почему так получилось

В таблице с ключом `ended_at` события всех стран идут в общем порядке времени. Поэтому оба запроса выбрали одинаковые 102 гранулы по дате. Фильтр по Германии применяется к прочитанным данным: страны нет в ключе.

В составном ключе сначала идёт страна, затем время внутри неё. Для Германии план использует оба поля и выбирает 8 гранул, один диапазон. Без ограничения страны индекс тоже работает по `ended_at`, но план показывает `generic exclusion search`, 114 гранул и 14 диапазонов. Нужный день расположен в разных группах стран, и чтение получилось больше.

### События, чтение и строки отчёта

На `hw_events_time` запрос по Германии нашёл 59 423 подходящих события и вернул одну строку. Запрос по всем странам нашёл 825 369 событий (сумма `events_total`) и вернул семь строк. Оба прочитали одинаковые 835.58 тыс. строк: по индексу выбраны те же гранулы. Число событий после фильтра и число строк после GROUP BY не определяют, сколько строк пришлось прочитать.

### Выбор ключа

Для исследованного отчёта по Германии выбираю `(country, ended_at)`, для отчёта по всем странам — `ended_at`, если сравнивать по объёму чтения. Чтобы выбрать один ключ для всей нагрузки, нужны частоты этих запросов, другие фильтры и отчёты, типичные периоды, распределение событий по странам, требования к записи и объёму хранения. Здесь проверялось чтение двух вариантов за один день; скорость выполнения не сравнивалась.
